# Private Cloud SAP 검증 키트

이 키트는 **미배포 체크아웃의 로컬 구현**이다. 실제 SAP에서 실행하거나
통과한 기록은 아직 없다. 사용 전 조직의 SAP API Policy 적용 범위, SAP의
승인된 경로, 권한과 운영 규칙을 검토한다. [정책 및 공존 안내](sap-api-policy-and-coexistence.md).

## 준비와 실행

1. 이 체크아웃을 빌드해 반입하거나 `npm run pack:runtime` 결과를 반입한다.
   Node.js 20 이상이 필요하다. 이 체크아웃의 `pack:runtime`은 설치된 런타임
   의존성을 함께 묶는다. macOS에서 격리 압축 해제 후 프로필 없는 시작을
   확인했으며, 대상 OS·아키텍처에서의 실행과 SAP 접속은 아직 검증되지 않았다.
   배포된 기존 2.2.0 npm 패키지에는 이 키트와 이후 로컬 변경이 없다.
2. 대상 환경에서 개발 프로필을 설정하고 자격 증명을 로컬에 저장한다.
   읽기 전용 검증 대상 클래스는 소스 조회가 허용된 기존 클래스를 지정한다.
   테스트는 개발 프로필만 허용하며, 쓰기 검증은 read-only 프로필에서도 거부한다.
3. 결과를 저장할 **빈 작업 디렉터리**에서 다음을 실행한다. 경로는 실제
   반입 위치로 바꾼다. 인자나 환경 변수에 비밀번호·토큰을 넣지 않는다.

```bash
node /path/to/sap-abap-mcp/scripts/run-private-cloud-acceptance.mjs \
  --profile DEV100 --class ZCL_APPROVED_READONLY
```

패키지 검색 패턴은 기본 `Z*`이며 `--package-pattern Z*`로 변경할 수 있다.
실제로 오래된 열린 Transport의 번호를 이미 알고 있다면, 로컬 보안 절차에
따라 `SAP_ACCEPTANCE_OLD_TRANSPORT` 환경 변수로 제공하면 500개씩 마지막 페이지까지 조회한 결과에
해당 번호가 포함되는지 별도로 확인한다. 값 자체는 결과 파일에 저장하지 않는다.
조회가 없거나 범위 밖이면 `unverified`이며 제품 결함이나 부재의 증거가 아니다.

임시 객체 쓰기를 허용하려면 같은 명령에 `--allow-tmp-write`를 추가한다.
이 플래그는 무작위 이름의 `$TMP` 클래스 생성, 해당 객체의 소스 수정·진단·
활성화·삭제를 요청한다. 생성 성공과 이름·유형·패키지·경로가 모두 일치한
객체만 수정과 삭제 대상으로 인정한다. `$` 치환 시퀀스를 활성 소스에서 다시
읽어 확인한다. 다른 기존 객체는 변경하지 않는다. 종료 전 삭제를 시도하며,
삭제 성공 응답과 후속 `OBJECT_NOT_FOUND` 확인을 구분한다. 생성 응답이
유실되거나 소유권을 확인하지 못한 경우 자동 삭제하지 않으며 `cleanup`을
`uncertain`으로 남긴다. 중단이나 네트워크 오류 후에는 운영자가 SAP에서
해당 계정의 최근 임시 객체를 직접 확인하고 소유권을 확인한 뒤 정리해야 한다.

## 결과와 범위

현재 작업 디렉터리에 `private-cloud-evidence.sanitized.json` 하나만 생성한다.
기존 파일은 덮어쓰지 않는다. 상태와 고정 단계명만 허용 목록으로 기록하며 SAP
URL, 호스트/IP, 사용자, 자격 증명, 고객 소스, Transport 번호, SAP 오류 원문과
입력값을 결과에 복사하지 않는다. 서버의 stdout/stderr와 doctor 출력은 메모리에서만
처리하고 파일이나 콘솔에 출력하지 않는다. 이 키트가 생성하는 결과 외에 운영
환경의 기존 SAP 감사 로그나 호스트 로그는 별도로 관리해야 한다.

- `passed`: 해당 단계의 제한된 확인이 성공했다. SAP 시스템 전체의 적합성을 의미하지 않는다.
- `failed`: 단계가 실패했다. 민감 정보가 남지 않도록 SAP 오류 원문은 포함하지 않는다.
- `unverified`, `incomplete`, `skipped`: 확인하지 못했거나 실행하지 않았다. 전체 `status`는 이 경우 `incomplete`다.
- `cleanup`: `verified_absent`, `receipt_only_unverified`, `uncertain`, `not_requested`를 구분한다. `receipt_only_unverified`는 삭제 증명이 아니다.
- 종료 코드: 0은 모든 단계 통과, 1은 실패, 2는 미완료다. 현재 의도적으로 건너뛰는 단계가 있어 정상적인 기본 실행도 2가 될 수 있다.

기본 실행은 `doctor --include-components`, 시스템 메타데이터, 패키지·클래스
검색, 클래스 소스·구조, Transport 목록, 덤프와 피드를 확인한다. 기존 제품의
시스템 메타데이터 경로는 일부 고정 SQL을 사용할 수 있다. 데이터 소스 차단
정책과 SAP 권한을 적용한다. ATC cached 도구는 **현재 서버 프로세스의 캐시**를
읽는다. 새 프로세스의 빈 결과는 ATC 통과가 아니므로 `unverified`다. 이 서버의
ABAP Unit 도구는 조회가 아니라 테스트 실행이므로 읽기 전용 기본 경로에서는
`skipped`로 기록한다.

2.2.0의 여덟 수정 중 `$` 보존은 선택한 임시 쓰기 경로에서만 검사한다.
오래된 Transport 검색은 지원·결과 범위 및 알려진 대상이 있어야 부분적으로
확인할 수 있다. Transport 릴리스, Transport 객체 추가, RAP 생성, V4 unpublish,
Dictionary 검사 및 최상위 이송 가능 패키지 생성은 `$TMP`의 일회성 클래스만으로
검증할 수 없어 `skipped`다. 이 키트는 그 여섯 항목의 라이브 통과를 주장하지
않는다. 각각의 격리된 실제 이송·객체·권한과 별도 검증 절차가 필요하다.

외부 반출 전 파일을 조직의 정보보호 절차에 따라 검토한다. 이 파일은 단계별
결과만 보존하므로 SAP 원문이 필요한 문제 분석은 내부 환경에서 수행해야 한다.


`--activation-diagnostics`를 `--allow-tmp-write`와 함께 지정하면 활성화 응답의
메시지 유형·클래스·번호가 모두 허용 형식일 때만 결과에 기록한다. 기본값은
기록하지 않는다. SAP가 해당 필드를 보내지 않거나 이름이 다르면 빈 배열이며,
메시지 원문과 객체 식별자는 기록하지 않는다. `buildId`는 스크립트와 빌드된
`dist/src` 파일들의 내용으로 계산한 SHA-256이다. 동일 커밋의 변경 작업본도 구분할 수 있지만 Git
커밋 ID는 아니다. 활성 소스 확인은 명시적으로 active 버전을 요청한다.

## 활성화 조사와 응답

단일 활성화는 대상 객체 URI·이름과 해당할 때 mainProgram을 전송하고,
일괄 활성화는 inactive 목록에서 얻은 URI·유형·부모 URI·이름을 전송한다.
두 경로 모두 preaudit를 요청한다. 이 차이가 이번 SAP 오류의 원인인지는
확인되지 않았다. 키트의 두 문자열 패치는 정확히 한 번만 일치할 때 적용되며,
문자열 검색만으로 클래스 구조의 의미를 증명하지는 못한다. 쓰기 후 활성화
검증은 명시적으로 active 버전을 읽는다. 단일 활성화는 기존 success·messages·
inactive 필드를 유지하면서 일괄과 같이 status와 objectResults를 추가한다.

`unit_test_previous_result`는 조회 API가 없어 실행하지 않는다. 임시 클래스에
대한 새 ABAP Unit 실행은 별도의 실행 권한과 테스트 설계가 필요하다. Transport
릴리스·객체 추가와 최상위 이송 가능 패키지 생성은 $TMP 범위를 벗어나며,
RAP·V4와 Dictionary 검사도 적합한 별도 격리 리소스가 필요하므로 이 키트에서는
모두 skipped다. 여섯 단계의 실제 SAP 성공을 추정하지 않는다.

## ATC worklist와 Transport 정규화 재검증

각 ATC 실행은 시스템 변형명으로 새 worklist를 만든다. 빈 worklist ID나
빈 값·전부 0인 run ID는 오류이며 결과 목록을 읽지 않는다. run ID가 생성한
worklist ID와 다르거나 `FINDING_STATS`가 반환된 대상 findings와 다르면 경고한다.
대상 외 worklist 객체의 findings는 제외하고 경고한다. 이 경고는 결과 누락이나
백엔드 차이를 조사해야 하는 신호이며, 경고가 없다는 사실만으로 완전성을
증명하지 않는다.

Transport ATC는 CTS 소유 객체를 기준으로 중복을 제거한다. 지원하지 않는
CORR 및 BW 항목은 `skipped`와 이유를 반환하고 게이트 집계에서 제외한다.
함수 모듈의 소속 그룹을 확인하지 못하면 오류로 남긴다. 일반 include의 메인
프로그램 조회가 실패하면 확인 가능한 include URI를 사용한다. 응답의
`atcTarget`과 `atc.notices`에서 대상과 경고를 확인할 수 있다. 동작은 목으로만
검증되었으며 실제 SAP 결과와 권한·서비스 가용성은 사내에서 별도로 확인한다.
